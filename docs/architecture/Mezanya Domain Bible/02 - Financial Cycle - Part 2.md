# 02 - Financial Cycle

## Part 2 — Money Flow Engine

> يشرح هذا الجزء كيف تنتقل الأموال داخل Mezanya منذ إنشاء العملية وحتى تحديث الكيانات المختلفة.

# مقدمة

لا يفرق المحرك المالي بين كون العملية يدوية أو متكررة، وإنما يهتم بما تمثله العملية من أثر مالي. لذلك فإن جميع العمليات تمر بنفس المنطق العام، ويختلف فقط مصدر إنشائها أو توقيت تنفيذها.

---

# الرسم 1 --- دورة إنشاء العملية

```text
User / Scheduler
        │
        ▼
Create Financial Operation
        │
        ▼
Validate Input
        │
        ▼
Resolve Targets
        │
        ▼
Apply Effects
        │
        ▼
Save Operation
        │
        ▼
Refresh State
```

كل عملية تبدأ بإنشاء كيان العملية نفسه، ثم يتم التحقق من البيانات المطلوبة، وبعد ذلك يحدد المحرك الكيانات المتأثرة قبل تطبيق الأثر.

---

# أنواع الإيداع

داخل Mezanya لا يوجد نوع واحد للإيداع، وإنما نفس العملية يمكن أن تستخدم في عدة سيناريوهات:

- إيداع لمحفظة فقط.
- إيداع مرتبط بمصدر دخل في الميزانية.
- إيداع لحصالة.
- إيداع لمخصص (إن سمح السيناريو بذلك).
- إيداع بدون محفظة عندما لا توجد حركة أموال حقيقية.

هذه المرونة ناتجة عن نفس محرك العمليات، وليس عن وجود محركات مختلفة لكل ميزة.

---

# الرسم 2 --- أهداف الإيداع

```text
Deposit
   │
   ├── Wallet Only
   │
   ├── Budget Income Source
   │
   ├── Jar
   │
   └── Allocation / Unallocated
```

---

# مصادر الدخل

مصدر الدخل ليس معاملة، بل كيان دائم داخل الميزانية.

يمكن أن ترتبط به عشرات العمليات:

```text
Salary
 │
 ├── Monthly Salary
 ├── Bonus
 ├── Incentive
 └── Manual Adjustment
```

ويظهر مجموع هذه العمليات كمصدر دخل واحد داخل تقارير الميزانية.

---

# الرسم 3 --- الراتب

```text
Recurring Schedule
        │
        ▼
 Pending Operation
        │
        ▼
 User Confirmation (if required)
        │
        ▼
 Execute Deposit
        │
        ▼
 Wallet / Budget
```

إذا كان مصدر الدخل متغيرًا (Variable Income)، فلا يوجد جدول زمني، وإنما ينشئ المستخدم عملية إيداع يدوية كلما حصل على دخل جديد.

---

# العلاقة بين المحفظة والميزانية

في السيناريو المعتاد، يدخل المال أولًا إلى محفظة، ثم يمكن ربط العملية بمصدر دخل داخل الميزانية.

لكن Mezanya يسمح أيضًا بإنشاء عملية بدون محفظة إذا كان المستخدم يريد تعديلًا منطقيًا داخل النظام لا يمثل حركة أموال حقيقية.

ولهذا فإن وجود المحفظة يعتمد على السيناريو الذي اختاره المستخدم.

---

# الرسم 4 --- أثر العملية

```text
Operation
    │
    ├── Wallet Effect
    ├── Budget Effect
    ├── Jar Effect
    └── Allocation Effect
```

ليس شرطًا أن تتأثر جميع الكيانات في كل عملية، وإنما يحدد المستخدم ما يرتبط بالعملية، ويطبق المحرك التأثيرات المناسبة فقط.

---

# التحقق من صحة العملية

قبل حفظ أي عملية يجب التأكد من:

- صحة القيمة.
- صحة التاريخ.
- صحة الكيانات المرتبطة.
- عدم تعارض البيانات.
- توافق نوع العملية مع الهدف المختار.

ويجب أن تكون جميع هذه القواعد داخل المحرك المالي وليس داخل واجهة المستخدم.

---

```text
 │         │

```

---

# تحديث الحالة

بعد نجاح العملية يقوم النظام بتحديث حالة الكيانات المتأثرة فقط، ثم يعيد حساب المؤشرات اللازمة ويحدّث التقارير.

لا يعتمد النظام على وجود منطق منفصل لكل شاشة، وإنما تستمد جميع الشاشات بياناتها من الحالة المالية الناتجة عن المحرك.

---

# قواعد هذا الجزء

1. جميع العمليات تمر بمحرك واحد.
2. نوع إنشاء العملية لا يغير منطق التنفيذ.
3. مصدر الدخل كيان دائم وليس عملية.
4. المحفظة اختيارية حسب السيناريو.
5. الكيانات المتأثرة تحددها بيانات العملية نفسها.
6. التحقق يتم داخل المحرك المالي.
7. واجهة المستخدم لا تحتوي قواعد الأعمال.
