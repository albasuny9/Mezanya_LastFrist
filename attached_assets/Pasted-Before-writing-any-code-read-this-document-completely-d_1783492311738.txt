==========================================================
ARCHITECTURE PRINCIPLE
==========================================================

The application has five independent domains.

Wallet

Responsible only for physical money.

--------------------------------

Budget

Responsible only for monthly planning.

--------------------------------

Transaction

Responsible only for financial history.

--------------------------------

Jar

Responsible only for reserved balances.

--------------------------------

Money Distribution

Responsible only for describing where Jar money physically exists.

These responsibilities must never overlap.

==========================================================
STEP 2
Build the Distribution Domain
==========================================================

Introduce a proper Distribution domain.

The architecture should revolve around Distribution Entries.

A Distribution Entry represents:

Jar

↓

Wallet

↓

Amount

plus optional metadata such as:

- linked transaction
- creation source
- manual / automatic origin

A Distribution Entry is NOT:

- a transaction
- financial history
- wallet balance

==========================================================
STEP 3
Separate responsibilities
==========================================================

Review the current code.

Where responsibilities overlap:

refactor gradually.

Examples:

Wallet should never own Jar logic.

Jar should never own Wallet logic.

Transactions should never own Distribution.

Distribution should become the bridge only.

==========================================================
STEP 4
Distribution Engine
==========================================================

Create or refactor the engine so it becomes responsible only for Distribution.

Allowed responsibilities:

- create entry
- edit entry
- remove entry
- move entry
- validate entry

Forbidden responsibilities:

- changing wallet balances
- changing transaction history
- modifying budget calculations

==========================================================
STEP 5
Integrity Validation
==========================================================

Create a validation layer.

It should detect problems only.

Examples:

Total Distribution != Jar Balance

Negative Distribution

Missing Wallet

Invalid references

Deleted linked transaction

Orphan Distribution

The validator reports problems.

It does NOT solve them automatically.

==========================================================
STEP 6
Migration
==========================================================

If migration is needed,

keep existing user data.

Prefer migration over recreation.
